# Development purchase placeholder

The user requested this on 2 October 2026: skip actual IAP linking because Google Play setup is not available, and provide a placeholder UI to test the feature. Real pack configuration, localized-price verification, receipt/billing tests and backend deployment are deferred. This is a development prototype, not storefront acceptance.

The authored pack IDs and quantities stay unchanged: `rr.kk.small.1000` (1,000 KK, example ₹99), `rr.kk.festival.6000` (6,000 KK, example ₹499), `rr.kk.celebration.13000` (13,000 KK, example ₹999), `rr.kk.grand.28000` (28,000 KK, example ₹1,999). All test buttons must say **Test purchase** and the shop must state **No real payment**. Prices are labeled examples; none are claimed as retrieved from Google Play. One draw still costs 100 KK with the existing 75/22/3 pool, no guaranteed rarity and no automatic spending.

`DevelopmentShop.cs` provides development-only engine commands to mark an isolated profile, begin one persisted pending operation, and resolve it as delivered, cancelled or failed. Pending means no currency has been granted. The user may leave it pending, restart and resume the same operation. Success saves the operation status and exact pack grant together before publishing state. Duplicate taps reuse that operation; duplicate or older callbacks cannot grant twice. Cancelled/failed operations cannot be delivered later. A save failure leaves the previous valid state and permits retry. Test purchases never affect cash earnings, Fame, free credits or real receipts.

The marker is kept when prestiging and blocks live premium preparation/reconciliation. Simulated KK can exercise the real local card pool after Talent unlocks, without creating gift provenance for a server import. The grant methods are excluded from ordinary Unity release compilation, and release state validation rejects a test-shop marker. An explicit release build with the lab symbol is rejected. Existing live authority/IAP code stays disconnected; no payment/network SDK is invoked by the placeholder.

Evidence: [505 current core checks](Core-Redesign.txt), including 38 development-shop checks; [11 actual Unity codec checks](Unity-Development-Shop.txt); [four compiler-symbol cases](Release-Symbols.txt); [34 native binding/render checks](Unity-Shop-UI.txt); [58 two-session Play Mode checks](Unity-Shop-Play.txt). The native implementation is complete as an isolated preview component. Main/device and comprehensive recovery acceptance remain RR-07-06, RR-09-07 and RR-11.

`RedesignShopScreen` uses the saved native prefab, a persistent TEST SHOP / No real payment banner and four content-bound packs. Browsing alone does not mark a profile or grant currency. Only an isolated guest in an Editor/development build can begin simulated purchases; account-bound and ordinary release views cannot grant. Pack buttons say Test purchase and prices say Example price / not charged. The test-state panel exposes ready/loading/unavailable; the pending panel offers success/cancel/failure or leaving it pending. No SDK, network call or real receipt is involved. The driver supplies its guest/profile boundary and saving retry; session ownership still gates all commands.

The Play Mode test uses two sessions and a real saved file: it leaves Small box pending, stops, reloads the same operation, delivers it once, tests all four pack totals (48,000 KK), rejects duplicate callbacks, cancels/fails without delivery and explicitly spends 100 KK for one actual Talent draw. Native binding checks also inject persistence failure and lost ownership, prove no grant is published, and retry the same operation. Reduced-motion/reveal behavior is covered by the separate Talent suite. All shop states preserve the serialized UI inventory.

A first restart run encountered a recoverable startup write failure after successfully reading the pending save. Its save/backup were valid and retained; a direct diagnostic write to that disposable file succeeded, and a fresh full two-session run passed all 58 checks. The first underlying I/O exception was not recorded, so no specific cause is asserted. `RedesignLifecycle.LastSaveException` now retains that local diagnostic for future failures. Integrated device acceptance must exercise this boundary too. The successful Play run records no gameplay/runtime error; the known installed MCP path-space startup advisory is recorded separately.

Reproduce with `BuildRedesignUI.AddShop` once for a staged prefab (fresh `Build` includes it), `RedesignShopValidation.Run`, then `RedesignShopPlayValidation.Start`. The latter manages two Play Mode sessions and restores the original scene. Real storefront product/price configuration, localized pricing, receipt/billing acceptance and backend deployment are still deferred; these simulated results do not establish Google Play acceptance.
