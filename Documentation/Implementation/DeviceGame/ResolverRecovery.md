# Generated Firebase dependency recovery

The initial full-game playtest APK was produced, but its Unity report contained three errors: a generated Auth POM metadata file could not be written, its metadata write failed, and dependency resolution reported failure. It was not installed or accepted. [Initial build report](Build-InitialResolverFailure.txt) and [initial package inspection](PackageChecks-Initial.txt) are preserved.

Standalone forced resolution reproduced transient writes against different generated POMs, including Windows error 1224 (mapped file). File permissions and the read-only attribute did not explain the failure. Releasing handles in a generated-asset postprocessor did not eliminate it, so that experimental postprocessor was removed.

The final incomplete App Check POM still declared `srcaar` while its generated artifact was an AAR. With the Editor idle, cached handles were released and the resolver's own `LocalMavenRepository.PatchPomFile` was applied to that existing generated file. It returned true; ordinary dependency resolution then returned true. No SDK source or project Firebase configuration was replaced. The existing `FirebaseRepositoryUriFix.cs` was preserved.

All seven generated AAR hashes match their corresponding local SDK `.srcaar` source bytes, and all generated POMs now declare `aar`; [verification](FirebaseGeneratedArtifacts.txt). The playtest build now resolves dependencies before scene serialization, validates generated POM/AAR completeness, and refuses acceptance unless BuildReport reports both success and zero errors. A clean rebuild is required; this is not a claim that the upstream force-regeneration/file-mapping race is permanently fixed.

Technical basis: Unity documents [ReleaseCachedFileHandles](https://docs.unity.com/en-us/engine/6000.3/script-reference/unityeditor/assetdatabase/releasecachedfilehandles) for file-sharing errors. The pinned resolver's [POM patch implementation](https://raw.githubusercontent.com/googlesamples/unity-jar-resolver/v1.2.189/source/AndroidResolver/src/LocalMavenRepository.cs) converts the generated packaging to the actual artifact extension. The installed SDK remains 13.17.0.

## Recurrence after the Talent correction

Ordinary preflight resolution later reproduced error 1224 while patching generated Crashlytics and Firestore POMs; the builder stopped before producing a new APK. That failed attempt is preserved in `Build-ResolverFailure-AfterTalentArt.txt`. A diagnostic attempt to batch the resolver inside `StartAssetEditing` also failed because its generated-directory/import operations require immediate AssetDatabase synchronization. That approach was not added to project code. A subsequent ordinary resolution, with imports enabled and cached handles released, succeeded and restored all seven AAR/POM pairs.

The builder now has one bounded recovery attempt after failed preflight: release cached handles for each existing generated POM, invoke the installed resolver's own packaging patch against the corresponding generated AAR, refresh, and require a second ordinary resolution to succeed. It still fails if either recovery or final resolution fails. Before BuildPlayer, it enumerates the local SDK `.srcaar` files and requires every generated AAR/POM pair, correct `aar` packaging, and exact SHA256 equality between source and generated library. It neither alters SDK sources nor suppresses dependency/build errors. This makes the recovery reproducible; it does not claim the upstream mapped-file race is permanently fixed.

The resolver's [copy/import sequence](https://raw.githubusercontent.com/googlesamples/unity-jar-resolver/v1.2.189/source/AndroidResolver/src/GradleTemplateResolver.cs) and Unity's [asset-edit batching contract](https://docs.unity3d.com/6000.4/Documentation/ScriptReference/AssetDatabase.StartAssetEditing.html) were reviewed while investigating this behavior. Production configuration and the pre-existing URI fix remain unchanged.
